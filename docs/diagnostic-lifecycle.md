# Диагностика: приглашение, попытка и отчёт

Обновлено: 4 октября 2026, Asia/Tashkent. Документ описывает реализованный жизненный цикл A2 и принятый stage-baseline P06. Ниже история исправления P04 отделена от действующей политики остановки. Происхождение образов, Git-фиксация и публикация на stage/production учитываются отдельно в release record.

## Источники состояния

Auth-service хранит приглашение и сводный результат ученика. Приглашение проходит `pending → confirmed → in_progress → completed`. Незавершённое приглашение после дедлайна получает `expired`. Код ссылки предоставляет доступ только к связанному ученику, классу и попытке.

Diagnostic-service хранит ответы, итоговую оценку и завершённый snapshot. PostgreSQL является источником завершённого результата. Redis содержит временное состояние незавершённой попытки. Фазы алгоритма: `warmup`, `navigation`, `deep_scan`, `precision_targeting`; завершение фиксируется как `completed`.

Отчёт — отдельный производный документ: `pending → generating → ready`, либо повторная подготовка/`failed`. Ошибка подготовки отчёта не отменяет сохранённые ответы и завершение попытки. Перенос результата в auth-service имеет отдельные состояния `pending → syncing → synced`, либо повтор/`failed`.

## Завершение и повтор запроса

Последний ответ, итоговый snapshot, строка задания на отчёт и задание на callback сохраняются одной транзакцией. Ошибка до commit откатывает все четыре записи; временное состояние позволяет повторить тот же ответ.

Отправка сериализуется Redis-lock и блокировкой строки сессии в PostgreSQL. После завершения точный повтор последнего `task_id` и `student_answer` возвращает тот же результат из PostgreSQL без повторной оценки, записи ответа или постановки заданий. Изменённый ответ/задание получает `409 TASK_OUT_OF_SEQUENCE`. `time_ms` повторного запроса не меняет сохранённую длительность.

Сохранённый результат доступен при проекциях приглашения `confirmed`, `in_progress`, `completed`, `expired`; проверяется принадлежность к ученику и классу. Terminal-приглашение не разрешает новый старт или новый ответ. Запрос, допустимый при проверке срока, может завершить сохранение после наступления дедлайна. Уже завершённую попытку можно восстановить после истечения ссылки и удаления состояния Redis.

## Восстановление фронта

`GET /api/v1/diagnostic/sessions/by-invite` возвращает состояние конкретной попытки. После refresh, повторного открытия ссылки или потери ответа на последний POST фронт сначала разрешает состояние этой попытки. Только явный `404 SESSION_NOT_FOUND` при `confirmed` допускает экран нового старта.

При сетевой ошибке отправки попытка и черновик сохраняются. Сервер возвращает текущий вопрос либо завершённый результат. Смена кода ссылки очищает предыдущий черновик и локальное состояние. При отказе загрузки отчёта UI показывает «Ответы сохранены», а повтор загружает тот же отчёт. Запоздавшие запросы другой ссылки/предыдущей проверки игнорируются.

Ошибки диагностического API имеют `detail.code`, `detail.message`, `detail.action`. Примеры: `INVITE_EXPIRED/contact_center`, `ANSWER_IN_PROGRESS/check_session`, `REPORT_FETCH_FAILED/retry`. Старые auth endpoints сохраняют свой совместимый контракт.

## Callback и остановка воркера

Callback завершения содержит `session_started_at` из PostgreSQL. Auth-service принимает его через защищённый внутренний endpoint. Если стартовый callback потерян, завершение может восстановить связь только после подтверждения приглашения, для начала не раньше подтверждения, не позже текущего времени и строго до дедлайна. Другая уже связанная `session_id` не заменяется.

Проекция завершения идемпотентна для той же сессии. Callback, прерванный после claim, возвращается в очередь после двух минут. Свежий claim не забирается другим воркером. Поздний ответ старого воркера не перезаписывает новый claim: проверяются статус, номер попытки и время начала.

Автоматическая доставка ограничена пятью попытками. После `failed` необходим явный повтор оператором после исправления причины. Наличие durable queue не означает бесконечное автоматическое восстановление. Старые строки с пустым `auth_sync_requested_at` не отправляются автоматически. Потеря Redis незавершённой попытки не создаёт новую попытку; API возвращает контролируемый отказ. Восстановление активной попытки из отдельного checkpoint — другой объём работ.

Логи переходов используют `invite_id`/`session_id`. Обычные сервисные HTTP-логи маскируют код в пути и параметре `invite_code`; callback warnings содержат тип ошибки/статус. Логи reverse proxy и Next.js требуют отдельной проверки на stage.

## Приёмка и публикация

Локальные проверки: PostgreSQL/Redis, auth и diagnostic через реальные HTTP endpoints, production-сборка Next.js и Chrome. Контент — синтетический HTTP fixture с одним вопросом; платные модели выключены. Это проверка жизненного цикла, не калибровки CAT или качества банка.

Кандидат не меняет схему БД и контент. Порядок stage-релиза: auth-service (поле callback), diagnostic-service (resolver/транзакция/воркер), затем frontend (новый resolver). Публикация требует решения владельца согласно корневому `CLAUDE.md`.

Перед публикацией сохранить SHA/digest прежних образов и конфигурации; собрать frontend с stage URL, поскольку локальный QA bundle использует loopback URL. На stage повторить ученик → итог → админский отчёт, таймаут/refresh, повтор callback, срок ссылки и viewport 360/768/1440. Сверить session_id и отсутствие дубликатов. Проверить редактирование схемы не требуется.

Для отката использовать сохранённые прежние образы: сначала frontend, затем diagnostic и auth. Проверенный откат на stage пока не заявляется. Возврат к старому diagnostic-коду возвращает исправленные здесь ошибки; перед откатом оценить незавершённые задачи очереди. Дамп банка для этой публикации повторно не восстанавливать.

## История P04: исправление runtime cap, 3 октября 2026

На этапе P04 был устранён runtime cap25: максимум стал 42 ответа суммарно, включая Deep Scan. В той версии раннее численное завершение требовало минимум 12 ответов, охват доступных основных L1-разделов исходного класса и SE≤0,30, вне Deep Scan. Завершение обхода разделов было приведено к общей stopping policy. Более поздняя ветка `classification_confident` добавлена в P06; её условия приведены ниже.

`MAX_ITEMS` в environment имеет приоритет над default в Settings. До P04 stage запускался с MAX_ITEMS=25 из `.env.preview`/compose; код с default=42 не менял runtime override. P04 изменил stage env/compose на 42 и согласовал warmup=5 и остальные baseline-параметры. Проверка выполнялась внутри работающего контейнера. Подготовленные local/production compose не означают публикацию production.

[Причина cap25 и приёмка P04](https://github.com/AurorixAI/algo-infrastructure/blob/CEO/docs/engineering/ROADMAP.md#a2-завершение-диагностики-и-приглашение).

## Действующая stage-политика P06: baseline на 4 октября 2026

Политика опубликована и принята на stage в P06 03.10.2026. Git-фиксация N00 не меняет правила и сама по себе не пересобирает текущий образ. Для следующего выпуска значения сверяются с environment/compose внутри целевого контейнера, а не только с defaults в Settings.

- **Общий максимум:** `MAX_ITEMS=42`, включая измерительные и prerequisite/Deep Scan ответы. Лимит проверяется первым и может прервать обязательный probe; тогда сохраняется `deep_scan_incomplete=true`.
- **Строгая ранняя остановка:** `MIN_ITEMS=12`, SE≤`SE_THRESHOLD=0.30`, достаточное покрытие исходного класса и отсутствие активного или pending критического Deep Scan. Причина — `precision_reached`.
- **Классификационная ранняя остановка:** минимум `CLASSIFICATION_MIN_ITEMS=20` общих ответов, SE≤`CLASSIFICATION_SE_THRESHOLD=0.40`, posterior mass выбранной CAT-категории≥`CLASSIFICATION_CONFIDENCE_THRESHOLD=0.90`, то же покрытие и отсутствие обязательного незавершённого probe. Причина — `classification_confident`.
- **Покрытие:** требуется `min(MIN_SECTION_COVERAGE=5, число доступных L1-разделов исходного класса)`. Засчитываются измерительные ответы в этих разделах; нижний класс из Deep Scan не заменяет их. Если в банке класса три доступных раздела, обязательное покрытие — три.
- **Разделение наблюдений:** Deep Scan расходует общий лимит и счётчик ответов, но не обновляет глобальную theta/posterior/SE. Его результаты проверяют prerequisite-навыки отдельно. Предварительная проверка pending probe не изменяет навигацию.

Завершение обхода разделов использует ту же stopping policy; само по себе оно не заменяет минимум ответов и покрытие. Если условия ещё не выполнены, начинается `precision_targeting`. Исчерпание банка сохраняет отдельную причину и не означает достижение строгой точности.

`phase=completed` означает сохранённую законченную попытку. `precision_reached`, `classification_confident` и `max_items_reached` — разные основания; `report_meta.precision_reached` истинно только для первой ветки. Классификационная mass относится к трём внутренним IRT-категориям по текущей модели, а не к пяти бизнес-статусам отчёта и не к эмпирической точности на учениках. Согласование этих шкал остаётся в плане. Максимум42 не является обязательной длиной, а новая ветка не обещает каждому сильному ученику завершение за20–25.
